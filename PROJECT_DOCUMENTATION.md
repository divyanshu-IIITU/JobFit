# JobFit Project Documentation

## 1. Project overview

JobFit is a web application that compares a candidate's resume with a job description. The user uploads a PDF resume, enters a job description, and receives matching suggestions generated by Google Gemini.

The project combines:

- Next.js and React for the web application
- TypeScript for the frontend and API routes
- Tailwind CSS for styling
- Python and PyPDF2 for PDF text extraction
- Google Gemini for resume and job-description analysis

## 2. Main functionality

The application provides these capabilities:

1. PDF resume upload through drag-and-drop or file selection.
2. PDF type and empty-file validation.
3. Temporary storage of the uploaded PDF.
4. Text extraction from every PDF page.
5. Job-description input through a textarea.
6. Resume and job-description matching through Gemini.
7. Display of the generated analysis in the browser.
8. User-friendly loading and error states.
9. Cleanup of temporary uploaded files after processing.
10. Local development and production build support.

## 3. How the application works

```text
User uploads PDF and enters job description
                    |
                    v
          React UploadForm component
                    |
                    v
          POST /api/extract-pdf
                    |
                    v
       Temporary PDF file is created
                    |
                    v
          Python process is started
                    |
                    v
       PyPDF2 extracts resume text
                    |
                    v
          POST /api/match with JSON
                    |
                    v
       Google Gemini analyzes the data
                    |
                    v
          Result is displayed to user
```

## 4. Important files

| File | Responsibility |
| --- | --- |
| `src/app/page.tsx` | Renders the homepage. |
| `src/app/components/UploadForm.tsx` | Handles file selection, job-description input, API calls, loading, errors, and results. |
| `src/app/api/extract-pdf/route.ts` | Validates the PDF, starts Python, collects extracted text, and removes the temporary file. |
| `src/app/api/match/route.ts` | Validates input and sends the resume and job description to Gemini. |
| `process_resume.py` | Extracts text from PDF pages using PyPDF2. |
| `requirements.txt` | Lists the Python dependency. |
| `package.json` | Defines JavaScript dependencies and run commands. |
| `.env.local` | Stores the private Gemini API key locally. |
| `README.md` | Contains setup and usage instructions. |

## 5. Detailed frontend behavior

The `UploadForm` is a client-side React component. It stores four main pieces of state:

- `file`: the selected PDF file
- `jobDescription`: the text entered by the user
- `result`: the Gemini response
- `isLoading` and `error`: request status and error information

The form uses `react-dropzone` to support drag-and-drop uploads. Only one PDF file is accepted. When the user submits the form, the browser performs two requests:

1. It sends the PDF as `multipart/form-data` to `/api/extract-pdf`.
2. It sends the extracted text and job description as JSON to `/api/match`.

## 6. PDF extraction process

The extraction route performs these steps:

1. Reads the multipart form data.
2. Confirms that the `resume` field is a non-empty PDF file.
3. Creates a unique temporary filename using `randomUUID()`.
4. Stores the PDF in the operating system's temporary directory.
5. Selects Python through `PYTHON_BIN`, `python`, or `python3`.
6. Starts `process_resume.py` as a child process.
7. Reads the Python process's UTF-8 output.
8. Returns the extracted text as JSON.
9. Deletes the temporary file whether processing succeeds or fails.

The Python script safely handles pages that do not contain extractable text by replacing `None` with an empty string. It also configures UTF-8 output so Unicode characters in resumes work correctly on Windows.

## 7. Gemini matching process

The match route:

1. Reads `GEMINI_API_KEY` from the server environment.
2. Parses the JSON request body.
3. Trims and validates the resume text and job description.
4. Creates a Gemini model client.
5. Sends both inputs in a matching prompt.
6. Returns Gemini's text response to the browser.

The API key is used only on the server and is not exposed to the browser.

## 8. Configuration

Create `.env.local` in the project root:

```env
GEMINI_API_KEY=your_gemini_api_key
```

If Python is not available on the system `PATH`, add:

```env
PYTHON_BIN=C:\Path\To\python.exe
```

Required installation commands:

```powershell
npm install
python -m pip install -r requirements.txt
```

Start the application with:

```powershell
npm run dev
```

## 9. Efficiency improvements in the project

The current implementation improves efficiency in several ways:

- PDF extraction is separated from Gemini matching, so each operation has a clear responsibility.
- The uploaded file is processed temporarily instead of being permanently stored by the API.
- The frontend prevents duplicate submissions while a request is active.
- The server trims and validates text before calling Gemini.
- The temporary file is deleted after processing to reduce disk usage.
- The app uses Next.js server routes, keeping the Gemini key off the client.
- The PDF is converted to text before being sent to Gemini, reducing the amount of data sent to the model compared with sending the original binary file.
- TypeScript strict checking catches many frontend and API mistakes during the build.

## 10. Current limitations and future improvements

The project is functional, but these improvements would make it more robust:

1. Add a maximum PDF file-size limit.
2. Add rate limiting and authentication before public deployment.
3. Return structured Gemini JSON containing a score, matched skills, missing skills, and recommendations.
4. Add automated tests for the Python extractor and API routes.
5. Improve error messages shown to users by forwarding safe server error details.
6. Add OCR support for scanned/image-only PDFs.
7. Move PDF extraction to a dedicated service if deploying to a host without Python support.
8. Cache repeated requests when the same resume and job description are submitted.
9. Add logging and monitoring for failed extraction and Gemini requests.
10. Update vulnerable npm dependencies regularly.

## 11. Ten interview questions and suggested answers

### 1. What problem does JobFit solve?

It helps candidates compare their resume against a job description and receive suggestions about their suitability, matching skills, and possible improvements.

### 2. Why did you use Next.js?

Next.js provides React-based UI development and server-side API routes in one project. This keeps the frontend and backend workflow together and allows the Gemini API key to remain on the server.

### 3. Why is the upload form a client component?

It needs browser features such as file selection, drag-and-drop events, React state, and `fetch`, so it uses the `'use client'` directive.

### 4. How does the application extract text from a PDF?

The Next.js extraction route saves the uploaded PDF temporarily and launches `process_resume.py`. The Python script uses `PyPDF2.PdfReader` to read every page and return the combined text.

### 5. Why use a separate Python process?

The project already uses PyPDF2 for PDF parsing. Running the extractor separately keeps PDF processing isolated from the TypeScript API route and allows Python PDF libraries to be used directly.

### 6. How is the Gemini API key protected?

The key is stored in `.env.local` and read only by the server-side match route. It is never placed in client-side code or sent to the browser.

### 7. What happens if the uploaded file is invalid?

The client accepts only one PDF file, and the server independently checks that the file exists, is non-empty, and has a PDF type or extension.

### 8. How does the app handle temporary files?

It creates a unique file in the operating system's temporary directory and deletes it after the Python process completes. Cleanup also occurs when an error happens.

### 9. How would you improve the Gemini response?

I would request a strict JSON response with fields such as match percentage, matching skills, missing skills, experience gaps, and recommendations. The server could then validate and display each field separately.

### 10. What would you test in this project?

I would test PDF extraction, empty and invalid uploads, missing environment variables, malformed JSON, Gemini failures, temporary-file cleanup, and the complete upload-to-result workflow.

## 12. Ten difficulties faced and how they were solved

### 1. Nested duplicate project folders

The project contained several nested copies. The working application was consolidated into `D:\Jobfit`, and the older copy was separated from the active source.

### 2. Next.js route return-type failure

The PDF route originally returned `Promise<unknown>`, which failed the production build. The route was given an explicit `Promise<NextResponse>` return type.

### 3. Linux-specific temporary directory

The original code used `/tmp`, which is not portable to Windows. It now uses Node's `os.tmpdir()`.

### 4. Linux-specific Python command

The original route always called `python3`. It now supports `PYTHON_BIN`, uses `python` on Windows, and uses `python3` on Unix-like systems.

### 5. Python dependency was missing

The extractor imported PyPDF2 without declaring it. A `requirements.txt` file was added.

### 6. Unicode output failed on Windows

Windows could use a CP1252 stdout encoding, which failed on some resume characters. The Python script now emits UTF-8.

### 7. Empty PDF page text caused errors

Some PDF pages return `None` from `extract_text()`. The extractor converts that value to an empty string before joining pages.

### 8. Legacy Express server duplicated the API

An unused `server.js` Express backend and its dependencies were removed because the active application uses Next.js API routes.

### 9. Missing Gemini configuration was unclear

The match route now checks for `GEMINI_API_KEY` and returns a clear configuration error instead of failing during initialization.

### 10. Project files and generated files were mixed together

The project now has a root-level `.gitignore` for dependencies, Python environments, build output, uploads, archives, secrets, and editor files.

## 13. Final project assessment

The application builds and runs locally, and the main request flow is implemented correctly:

```text
PDF upload -> text extraction -> Gemini analysis -> displayed result
```

Before production deployment, the highest-priority work is adding upload limits, rate limiting, automated tests, structured Gemini output, and updating vulnerable dependencies. The current Python subprocess design is suitable for local development or a server with Python installed, but deployment hosting must support both Node.js and Python.

## 14. Advanced technology interview questions

### 11. Why are the API routes implemented inside the Next.js App Router?

The App Router allows the UI and backend endpoints to live in one application. The routes in `src/app/api` execute on the server, so sensitive operations such as reading the Gemini key, writing temporary files, and starting Python do not need to happen in the browser. It also removes the need for a separate Express server and avoids cross-origin configuration during local development.

### 12. What is the difference between the server component and client component in this project?

`page.tsx` is a server component by default and renders the page shell. `UploadForm.tsx` is explicitly marked with `'use client'` because it uses React state, browser file objects, drag-and-drop events, and `fetch`. Keeping the form client-side prevents unnecessary client behavior from being added to the page shell.

### 13. Why should the Gemini call stay on the server?

The Gemini API key must not be exposed in browser JavaScript. A client-side Gemini call would allow anyone to inspect the key and use it outside the application. The server route acts as a controlled boundary: it validates inputs, reads the private environment variable, calls Gemini, and returns only the result needed by the UI.

### 14. Why is `multipart/form-data` used for the first request and JSON for the second?

The first request contains binary PDF data, so `FormData` and `multipart/form-data` are appropriate. After extraction, the data is plain text, so JSON is simpler and more readable for the matching endpoint. Separating these requests also makes PDF processing independent from AI matching.

### 15. Why is `spawn` used instead of reading the PDF directly in TypeScript?

`spawn` starts Python as a separate process and provides independent stdout, stderr, exit-code, and error events. This lets the Node route use PyPDF2 without mixing Python execution logic into TypeScript. It also makes failures observable: the route can distinguish a process-start failure from a non-zero PDF-extraction result.

### 16. What are the risks of starting a child process from an API route?

The process can fail if Python is unavailable, the script path is wrong, or the host blocks subprocesses. It can also consume CPU and memory if many requests arrive at once. The route therefore needs input-size limits, rate limiting, process timeouts, cleanup, and a deployment environment that supports Python. The current project handles cleanup and process errors but still needs limits and timeouts for production.

### 17. How does TypeScript help in this project?

TypeScript catches incorrect route return types, invalid component props, and many API integration mistakes before runtime. For example, the PDF route previously returned `Promise<unknown>`, which caused the production build to fail. Adding the explicit `Promise<NextResponse>` return type made the route contract compatible with Next.js.

### 18. Why are server-side validation and client-side validation both necessary?

Client validation improves the user experience by rejecting obvious mistakes immediately. It cannot be trusted for security because users can bypass browser code and send requests directly. The API routes repeat important validation on the server, including checking the uploaded file, required text, and API configuration.

### 19. How would you make Gemini output reliable for a user interface?

Instead of asking for unrestricted text, I would define a response schema containing fields such as `matchScore`, `matchedSkills`, `missingSkills`, `experienceGaps`, and `recommendations`. The server would validate the response before returning it. The UI could then render cards, score indicators, and lists instead of displaying one unstructured text block.

### 20. How would you deploy this application safely?

First, I would identify whether the hosting platform supports a persistent Node.js server, Python subprocesses, temporary files, and the required environment variables. Then I would add upload limits, rate limiting, authentication, structured logging, and dependency scanning. I would deploy a staging version, test PDF extraction and Gemini failure cases, and only then expose the application publicly.

## 15. Detailed problem-solving case study

One of the most important problems in the project was that the application appeared to work during development but failed when its production build validated the API routes. The issue was not solved by guessing; it was investigated in stages.

### Problem statement

The user could open the page, but the production build failed while checking the PDF extraction route. The error indicated that the route handler returned `Promise<unknown>` instead of a valid response type.

### Step 1: Observe the exact symptom

I first ran the same command used for production validation:

```powershell
npm run build
```

The important evidence was the Next.js type error pointing to the generated route types. This showed that the issue was not a browser rendering problem or a Gemini response problem; it was a route-handler contract problem discovered during compilation.

### Step 2: Form several hypotheses

Instead of immediately changing the return statement, I considered multiple possible causes:

- The route might return different types from different branches.
- A manually created `new Promise()` might not have a declared generic type.
- The route might be using an unsupported runtime.
- The request could be reaching an older duplicate copy of the project.
- The TypeScript configuration might be producing an incorrect generated type.

This list prevented the investigation from focusing on only the first familiar explanation.

### Step 3: Confirm which project was actually running

The workspace contained nested `JobFit` folders and two application copies. I compared their manifests and source hashes and checked the Git roots. This confirmed that the active project was the inner Next.js application and that the duplicate contained older versions of the same files.

### Step 4: Trace the route's return paths

I inspected the PDF route and followed every branch:

1. Missing file returns `NextResponse.json`.
2. Successful Python completion returns `NextResponse.json`.
3. Failed Python completion returns `NextResponse.json`.
4. The outer `try/catch` returns `NextResponse.json`.
5. The enclosing `new Promise` had no explicit response type.

The branch values looked like responses, but TypeScript inferred the promise as `Promise<unknown>` because the promise itself was untyped. This connected the source code to the exact build error.

### Step 5: Check related runtime problems instead of fixing only the compiler error

While tracing the route, I found additional issues that could appear immediately after the type error was fixed:

- The temporary directory was hard-coded as `/tmp`.
- The process command was hard-coded as `python3`.
- The Python script path was relative to the current working directory.
- Python stderr was logged but not returned as a useful server diagnosis.
- The uploaded file was not fully validated.

These were treated as separate findings, so the final change solved the route contract and the likely Windows runtime failures together.

### Step 6: Verify the Python environment independently

The route depends on Python, so I checked the selected interpreter rather than assuming that the terminal's default Python was correct. The configured interpreter was Python 3.14.2. I then checked whether PyPDF2 was importable and discovered that it was not installed in that exact interpreter.

This explained why a successful TypeScript build alone could not prove that resume processing worked.

### Step 7: Reproduce the extractor with a real PDF

After installing the declared dependency, I ran the Python script against a real uploaded resume. That test exposed a second runtime issue: Windows CP1252 output could not encode a Unicode character from the PDF. The script was then changed to emit UTF-8, and the same real PDF produced 58 lines and 3,897 characters successfully.

### Step 8: Apply the fixes at the source of each problem

The fixes were applied where the incorrect behavior originated:

- The promise was typed in the route rather than suppressing the build error.
- `os.tmpdir()` was used instead of a platform-specific path.
- Python selection was made configurable with `PYTHON_BIN`.
- The Python script normalized empty page text and emitted UTF-8.
- `requirements.txt` declared PyPDF2.
- Server-side file and text validation was added.

### Step 9: Validate the complete change

Validation was performed at several levels:

```powershell
npm run lint
npm run build
python -m py_compile process_resume.py
python process_resume.py <real-pdf-path>
```

The lint check, production build, Python syntax check, and real PDF extraction all passed. This combination was stronger evidence than checking only whether the homepage loaded.

### Step 10: Record remaining risks honestly

The investigation also showed that local success does not guarantee safe public deployment. The application still needs upload-size limits, rate limiting, authentication, dependency updates, and a hosting platform that supports Python subprocesses. Recording these remaining risks is part of completing the investigation rather than claiming the problem is solved permanently.
